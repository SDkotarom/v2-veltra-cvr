後半の方針：操作への反応Second-half plan: response to taps

作成 2026-10-06 ／ Suki さんに共有する前の社内メモWritten 2026-10-06 · internal notes before sharing with Suki

着手状況Where things stand

  • ローディング中のリング回転に関係する施策の多くは、9/4 の調査で起票したまま「open（計画中）」で、担当が牧野のまま。実装する人も見積もりも決まっていない
  • 9月に手を付けた②の施策は UX_DESIGN-309 の1件だけ。絞り込みの待ち時間は 1.82秒 → 0.97秒 で、効くことは確かめられた
  • つまり②は「やってみて効かなかった」のではなく、ほとんど着手できていない
  • 予算は半分ほど残っている
  • Most spinner-related items were written up on 9/4 and are still open, assigned to Makino. No implementer and no estimates yet
  • Only one response-side change shipped in September: UX_DESIGN-309, filter wait 1.82s → 0.97s. It proved the approach works
  • So the response side did not fail — it has barely been started
  • About half the budget is left

見立てReading

1. 実ユーザーは、サーバーの返事を待たされている（推定）1. Real users are waiting on the server (inference)

PSI（テスト環境）PSI (lab)実ユーザー（9/26 締め）Real users (week ending 9/26)合格ラインTarget

  • PSI ではサーバーの返事が速いのに、実ユーザーでは何倍も遅い。8/22 の週から3ページとも悪くなっている
  • PSI はキャッシュが効いた状態で測れていて、実ユーザーはキャッシュを外していることが多いと見ている（推定）。9/4 の調査の「キャッシュが通貨・端末・国などで細かく分かれすぎている」「絞り込み条件が付くとキャッシュを読まない」と合う
  • PSI を上げる施策では、実ユーザーの一番大きな待ちに届かない。サーバーの返事を速くすれば、①表示の速さと②ローディング中のリング回転の両方に効く
  • 地域・カテゴリーは事情が違う。PSI 上のサーバーの返事は速く、重いのはブラウザ側（画像・JS）。ここは別の見立てが要る
  • Server response is fast in PSI but several times slower for real users, and it has worsened on all three pages since the 8/22 week
  • PSI likely hits a warm cache while real users often miss it (inference). This fits the 9/4 finding: cache keys split by currency, device, country and so on, and filtered views skip the cache
  • PSI-focused fixes don't reach real users' biggest wait. Faster server response helps both load speed and spinner time
  • Region and Category differ: their server response in PSI is fast and the weight is in the browser (images, JS). They need their own reading

2. ローディング中のリング回転は「速くする」より「出さない」2. Remove spinners rather than speed them up

  • 9/4 の棚卸しでは、ローディング中のリング回転の多くが要らない待ちだった。表示済みの一覧の取り直し、「戻る」のたびの全読み直し、中身が空の通信など
  • 1件ずつが秒単位。9月の施策（PSI で数点〜20点）とは効き方の桁が違う
  • The 9/4 inventory showed most spinners are unnecessary waits: re-fetching lists already shown, full reloads on browser back, empty requests
  • Each is worth seconds — a different order of magnitude from September's PSI gains

3. 測り方を変えないと、②の効果は見えない3. Without new measurement, the response side stays invisible

  • TBT は「読み込み中に画面が固まっていた時間」。ローディング中のリング回転は「サーバーの返事待ち」なので TBT には出ない
  • UX_DESIGN-309 の効果が見えたのは、Suki さんが手で測ったから。手計測に頼る限り、②は「やってもやらなくても同じ」に見える
  • ローディング中のリング回転が出てから消えるまでの時間を、実ユーザーで直接測る（UX_DESIGN-425）
  • TBT is time the screen was frozen during load. A spinner waits on the server, so it doesn't show up in TBT
  • UX_DESIGN-309's effect was visible only because Suki timed it by hand. Relying on that makes the response side look like it changed nothing
  • Measure spinner time directly from real users (UX_DESIGN-425)

  • UX_DESIGN-398: shorten the VWO setting that blanks the screen for up to 2s. Big effect, but needs marketing's agreement first
  • UX_DESIGN-307: the first JS-reduction change. The investigation found no large reduction opportunity (see weekly note W41)

まだチケットに無い案Ideas not yet ticketed

  • 全画面のローディング表示を、一覧部分だけの表示に変える（9/21 に Suki さんが挙げていた案）。待ち時間は同じでも、ページ全体は止まらなくなる
  • 予約モーダルの絞り込み（9/4 の調査で 772.9ms と計測、改善の余地あり）
  • カードを押した時点で、AC詳細の取得を始める
  • Show the loader on the listing only, not full screen (Suki's idea on 9/21). Same wait, but the page stays usable
  • Booking modal filter (772.9ms measured on 9/4, room to improve)
  • Start fetching AC detail as soon as a card is tapped

目標の置き方（提案）Targets (proposal)

  • ① 主要ページの PSI を「低」から「普通」（50点以上）へ。実ユーザーのサーバーの返事を 0.8秒に近づける
  • ② 主要なローディング中のリング回転（カテゴリー・検索の絞り込み、AC詳細への遷移）を1秒以内
  • どちらも私の案で、根拠のある数字ではない。Suki さんと決める
  • Load: main pages from low to average in PSI (50+); bring real-user server response toward 0.8s
  • Response: main spinners (category and search filters, move to AC detail) within 1s
  • Both are my proposal, not evidence-based targets; to be set with Suki

結果は「リリース前」と「月末」の差で決めている。差が日ごとのばらつき（同じページの日ごとの標準偏差）以内なら変化なし。速くなった 3ページ／変化なし 2ページ／遅くなった 1ページ。The result compares before with month end. A change inside the daily spread (standard deviation of that page across days) counts as no change. Faster 3, no change 2, slower 1.
