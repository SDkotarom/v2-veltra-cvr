# レポート作成

## このスキルが解こうとしている問題

このリポジトリには 78 ページのレポートがある。作り方は `docs/playbook.md` に細かく書いてある。
それでも実測すると、CLAUDE.md が「絶対守る」としている UI 規則に **889 件の違反**があり、
配色は 3 系統、週次サマリーのクラス語彙は W20 を境に別物に分裂していた。

原因の切り分けは明確だった。

| 領域 | 仕組みの有無 | 結果 |
|---|---|---|
| 数値と data.json の整合 | `validate-report.py` がある | 最新週まで**崩れていない** |
| UI 規則・クラス語彙・配色 | 文章の規則だけ | W20 以降で**崩壊** |

つまり文章で規則を書いても守られない。**判定できる形に落とし、毎回走らせる**しかない。
このスキルはその線引きと、線の両側をつなぐ手順を持っている。

## 役割分担（これが安定化の本体）

迷ったらこの表に戻る。プログラム側の列にあるものを手で決め始めたら、そこがズレの入口。

| 決めること | 担当 | なぜそちらか |
|---|---|---|
| ページ構造・セクション順・見出し階層 | プログラム（雛形） | 毎回考え直すと必ずブレる。構造は論点ではない |
| 配色・フォント・余白 | プログラム（`report.css` の `:root`） | 「それっぽく」当てると意図が壊れる。実際に3系統に分裂した |
| クラス名 | プログラム（共有 CSS にあるものだけ） | 存在しないクラスは無言で効かない。崩れて初めて気づく |
| 数値の取得 | プログラム（GA4 MCP → `data.json`） | 手打ちは誤りの温床 |
| KPI の前週比・増減の向き | プログラム（`new-report.py`） | 色の出方を人が決める必要がない |
| 数値とページの整合 | プログラム（`validate-report.py`） | 目視では追えない |
| UI 規則の遵守 | プログラム（`lint.py`） | 文章の規則は守られない（実測済み） |
| 埋め忘れの検出 | プログラム（`check.py`） | 未置換の `{{...}}` が公開されるのを防ぐ |
| 結論の文言 | **AI** | 観察を 1 文にするのは判断。ここが仕事の中身 |
| 情報の階層 | **AI** | 何が並列で何が全体像かは中身次第 |
| Evidence の軸の選択 | **AI** | どの 3 軸が効くかは週によって変わる |
| アクションの粒度と優先順 | **AI** | 短期 / 中期 / 監視の割り振りは判断 |
| データ品質の疑い | **AI** | 異常値を見て bot か実態かを判断する |

## 手順

### 1. どの種別か決める

| 種別 | 置き場所 | 雛形 | 固有の作法 |
|---|---|---|---|
| 週次サマリー | `2026h1/reports/{YYYY}-{h1\|h2}/{YYYY}-w{WW}/index.html` | `assets/weekly-summary.html` | `docs/playbook.md` Phase 2.9。データ品質チェックが先 |
| スポット分析・単発レポート | `2026h1/spot/*.html` | `assets/analysis-report.html` | 節数は論点の数で決める |
| プロジェクトブリーフ | `2026h2/projects/*.html` | `assets/analysis-report.html` | `references/page-types.md` |
| 施策ドキュメント | `2026h1/planning/*.html` | `assets/analysis-report.html` | CLAUDE.md「施策ドキュメント執筆ルール」が優先 |

種別ごとの違いは `references/page-types.md` に書いてある。週次を作るなら
`docs/playbook.md` の Phase 2.9 を読む。このスキルはそれを置き換えない。

### 2. 雛形から起こす

既存ページをコピーしない。コピー改変が語彙分裂を生んだ経路そのもの。

```bash
# 週次（data.json から KPI と BN タイトルを機械的に埋める）
python3 .claude/skills/report/scripts/new-report.py --week 2026-w26

# 単発
python3 .claude/skills/report/scripts/new-report.py \
    --type analysis --out 2026h1/spot/my-report.html \
    --title "タイトル" --kicker "スポット分析" --period "2026-09-01 〜 2026-09-14"
```

実行すると「機械が埋めた値」と「判断が要る箇所」が一覧で出る。後者があなたの仕事。

### 3. 書く

雛形のコメントに、その枠が何を受けるかと、書き方の落とし穴が書いてある。
特に外しやすい 3 点。

**結論はユーザー行動の観察を主文に、数字は補強に回す。**

- NG: `CVR は 1.41% → 0.94% に崩落。②→③ が -5.84pp。`
- OK: `商品ページに来ても「予約を検討する」ところまで進まないユーザーが急増した週。来訪は倍近く増えたのに予約数はほぼ横ばい。`

数字を消すのではなく、解釈と並べる。数字だけの羅列は読み手に判断を投げている。

**冒頭で全体像を出す。** 結論を後ろに置くと、読まれない場所に結論が埋まる。
節を増やすのは 02 以降。

**インライン `<style>` を書かない。** 足りないコンポーネントがあるときは
`summary.css` に 1 度追加する。ページごとに足すと、W20 以降に起きたとおり
同じものを指す名前が何通りもできる。

### 4. 検証する

```bash
python3 .claude/skills/report/scripts/check.py 2026h1/spot/my-report.html
python3 .claude/skills/report/scripts/check.py --week 2026-w26
```

NG が出たら直す。指摘されてから直すのではなく、出す前に自分で回す。

### 5. 公開する

CLAUDE.md「公開フロー（Artifact）」に従う。`build.py` がリンク切れと上限も見る。

## 提出前チェック

### 機械が見る（`check.py` が自動で見るので、自分で確認し直さない）

未置換の `{{...}}` / インライン `<style>` / 共有 CSS に無いクラス / `report.css` の読み込み /
結論が最初のセクションか / GA4 出典と期間の表記 / UI 規則（左罫線・絵文字・行頭アイコン・
裸のチケット番号・13px 未満） / 週次の数値整合

### 人が見る（機械では代われない）

- 結論のヘッドラインが「ユーザーが何をしていたか」で始まっているか
- Evidence の 3 枚が別々の軸を見ているか（同じ話を 3 回していないか）
- Action の粒度が揃っているか（レイヤーで割るか対象で割るか、混ぜていないか）
- 前週・前回との連続性に触れているか
- 年次比較を含むなら、CLAUDE.md「YoY/前年比較の作法」の 3 原則を守っているか
- 説明文で埋めていないか。レイアウトと見出しで分かるなら本文は削る

## やってはいけないこと

- **既存ページをコピーして始める。** 雛形から起こす。コピーは分裂の経路
- **ページ内の `:root` で配色トークンを作る。** 配色の正は `report.css` だけ
- **共有 CSS に無いクラス名を使う。** 効かないまま公開される
- **`check.py` を飛ばして完成報告する。** 「整えました」は機械チェックが通ったことを指す
- **`data.json` の数値をページに手打ちする。** `new-report.py` に埋めさせる
