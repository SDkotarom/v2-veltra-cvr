データ・リーガル対応

計測とデータ取り扱いの健全化・法令順守。GDPR（同意の既定宣言）／ GTM コンテナの断捨離・統合 ／ 第三者提供データの棚卸し の 3 テーマは、独立タスクではなく ひとつのワークストリーム。タブで切り替えて全体像を追える。

順序の前提： Phase 0（同意の既定宣言） がすべての土台。これを固める前に GTM 統合や個別同意設定を進めると全やり直しになる。GTM の断捨離と第三者提供の棚卸しは Phase 0 を妨げない「掃除」として並行で進める。

GDPR対応 / 同意の既定宣言 と 法務パッケージ切替 最優先

英語サイトで完成済みの「同意の既定宣言」と法務文書パッケージを、日本語サイトにも適用する。Phase 0 が最優先である理由と、なぜ順序を戻せないのかを共有するための方向性メモ。

優先度：最優先 主導：二木さん ／ サイト側調整：Kotaro 更新：2026-07-30
01

結論

日本語サイトは、ページ表示と同時に 同意前から外部へデータが出ている 状態にある。実測では 29 ホスト に接続し、12 個のクッキーが同意を取る前に書き込まれ、接続先のうち 13 社がプライバシーポリシー上に記載がない。

英語サイトは新しい法務パッケージで既にこの状態を解消済み。日本語サイトだけが取り残されている。

最初に着手すべきは Phase 0：同意の既定宣言。ここで「Veltra は同意を取るまで計測・第三者提供タグを発火させない」という既定を宣言してから、GA 統合・GTM 統合へ進む。この順序は戻せない ―― 既定を決める前にタグを動かすと、後工程が全部やり直しになる。

02

なぜやるか

Traveler の閲覧・行動データを外部ベンダーへ渡す行為は、個人情報保護法上の 第三者提供 にあたる。第三者提供には 3 年間の記録保存義務があり、「いつ・誰に・何を・どの同意根拠で渡したか」を説明できる状態を常に保つ必要がある。同意の既定を宣言しないまま計測タグが動き続けると、この説明責任を果たせない。

さらに、日本語サイトと英語サイトでは 管理者法人が異なる（東京 と ホノルル）。言語で管理者が違うという矛盾は、コンテナ統合の局面で必ず突き当たる。ここを曖昧にしたまま統合を進めると、どちらの法人がデータ管理者として同意を取っているのかが説明できなくなる。だから統合の前に、同意の既定と管理者の整理を先に片付ける。

要するに： これは「法令を守るための最低ライン」であると同時に、後続の GA 統合・GTM 統合を安全に進めるための 土台工事。土台がないまま上物を積むと崩れる。

Phase 構成（4 フェーズ）

二木さんブリーフ（限定公開 →）の 4 フェーズ。上から順に着手する。番号が優先順位であり、Phase 0 を完了させないと Phase 1 以降は本来やり直しになる。

PHASE 0最優先

日本語ページで「同意の既定」を宣言する

「同意を取るまで計測・第三者提供タグは発火しない」を既定として宣言し、同意管理の土台を日本語サイトに敷く。ここが全ての起点で、以降のフェーズはこの宣言の上に載る。

PHASE 1高

GA の日本語プロパティを 1 本にする

複数に分かれた日本語計測プロパティを 1 本へ集約し、同意の既定に沿った計測に揃える。データの持ち主と流れをシンプルにしてから次へ進む。

PHASE 2中

GTM コンテナを新しい作りへ寄せる

現行コンテナを、同意の既定を前提とした新コンテナの作りへ統合していく。第三者提供データの棚卸し（40 社台帳）はこの工程の準備にあたる。→ GTM 断捨離・統合タブへ

PHASE 3低

統制を恒久運用に載せる

新規タグの追加・同意設定のチェックを、一度きりの整理で終わらせず継続運用の仕組みに載せる。棚卸しと承認のフローを定常業務化する。

03

いま進めていいこと / いま待つべきこと

判断基準はひとつ ―― Phase 0（同意の既定宣言）を妨げないか。妨げない掃除は進める、土台に依存する再構築は待つ。

✅いま進めていい（Phase 0 を妨げない範囲）

  • 明らかに死んでいるタグの停止。提供終了済みの計測サービス（例：提供元がサービス終了した Google Optimize）や、参照先の消えたツール向けタグなど、発火しても意味のないものを止める。
  • 管理者不明タグのヒアリング。40 件の管理者不明タグの持ち主を洗い出す。第三者提供データの棚卸しに接続。→ 40社台帳タブへ
  • 停止は Pause で統一。削除ではなく一時停止で揃え、削除は棚卸し完了後にまとめて行う。

⏸いま待つべき（Phase 0 完了待ち）

  • 新コンテナへの統合作業そのもの。同意の既定が固まる前に移すと全やり直し。
  • タグ側の個別同意チェック設定。既定が決まってからでないと設定基準が定まらない。
  • 大量のタグ再構築。土台（Phase 0）に依存するため、順序を守る。
やり直しリスク： Phase 0 を飛ばして統合や個別同意設定を進めると、同意の既定が変わった瞬間に設定基準ごと崩れる。「掃除は先、再構築は後」を厳守する。
04

検証の規律（二木さん設定）

タグを止める・消すときに事故を出さないための作業ルール。

  • 止めるときは「作成 → 確認 → 削除」の順。いきなり消さず、代替を用意して動作を確認してから消す。
  • 実ブラウザで測る。設定画面上の想定ではなく、実際のブラウザで発火・接続を確認する。
  • GTM は版を作ると作業場が固定される。下書きの上限は 3 つ。版管理を意識して並行作業を増やしすぎない。
  • 土台タグは参照側から順に消す。他タグが依存する初期化タグは、依存している側を先に外してから消す。
安全側の既定： 迷ったら Pause。削除は棚卸しと動作確認が揃ってから。停止したタグは記録を残し、いつでも戻せる状態にする。
05

MCP 接続の現状（AI 管理の実装方式）

  • 公式の GTM MCP は存在しない。そのまま繋げる標準ツールは今のところない。
  • 調査は GTM API v2 経由で実施済み。二木さんが API v2 でコンテナ状態を取得・棚卸ししている。
  • 「MCP 経由で AI 管理」の実装方式は要確認。社長方針の AI 管理をどの経路（API ラッパー等）で実現するかは、二木さんに確認してから設計する。
セキュリティ観点： API 経由で GTM を操作する場合、認証情報はコードへ直書きせず（ハードコード回避）、権限は必要最小限のスコープに絞る。操作は監査ログが残る形にする。

02

この棚卸しの位置づけ

この作業は単独のタスクではなく、Phase 2（GTMコンテナを新しい作りへ寄せる）の準備工程にあたる。統合の前に「何を外部へ渡しているか」を台帳で確定しておかないと、新コンテナへ移すべきタグ・止めるべきタグの判断がつかない。

  • Phase 0（同意の既定宣言）と並行して進められる ―― 棚卸しは掃除であり、Phase 0 の土台を妨げない。→ GDPR タブへ
  • GTM の断捨離と表裏一体 ―― 管理者不明タグのヒアリングは、断捨離の「いま進めていいこと」に含まれる。→ GTM 断捨離・統合タブへ
  • 個人情報保護法の第三者提供記録（3 年保存義務）を満たすための、説明可能性の担保でもある。
03

優先 ★7 件 ― 台帳に書くこと

個社名・台帳シートの URL は非公開（社長指示）。ここでは記入すべき列と判断基準を共有する。★7 件は「管理者不明」または「送信先の性質が要判断」のタグ。

台帳列何を書くか判断基準
R 列 用途・データ内容そのタグが何を計測し、外部の誰へ何を渡しているか。ヒアリングで判明した用途を記入。「用途を 1 文で説明できるか」。説明できないものは要停止候補。
S 列 停止可否止めても事業影響がないか。可 / 不可 / 要確認 を記入。回答あり＝管理者判断に従う。無回答＝停止（既定）。
T 列 対応方針Pause / 新コンテナへ移設 / 継続 のいずれか＋実施予定。Phase 0 完了前は Pause か据え置きのみ。移設は Phase 2 で。
無回答の既定： 期限までに用途の回答が得られない送信先は S 列「停止」、T 列「Pause」で確定する（社長承認済み）。用途不明のまま外部へデータを出し続ける状態を残さない。

Mobility Hub｜計測セットアップ

mobility.veltra.com（別ドメイン・別GA4プロパティ・予約も mobility で完結）の計測設計。専用 GTM コンテナで分離するのが推奨。

担当：Kotaro ／ Sachie 更新：2026-07-31
01

結論

Mobility 専用の GTM コンテナ＋専用プロパティで分離を推奨。現行 v2（241本）をコピーせず、同意の既定を最初から敷いた新世代の作りで。二木さんに一言共有。

予約も mobility で完結するため、CVR・予約数・売上は Mobility プロパティで直接取れる（クロスドメイン不要）。残る論点は購入後のマイページ（カレント）横断のみ。

02

やること

  • A 設計 — KPI確定／命名・オーナー／二木さんへ共有
  • B 実装 — 専用コンテナ作成／GA4 ファネル＋purchase（transaction_id・value・items）／同意ゲート（同意前タグ発火なし）／二重計上防止
  • C 検証・公開 — 実ブラウザで検証（同意挙動含む）→ 共有
  • D 将来 — 顧客横断（LTV・リピート）が要れば sid 方式（.veltra.com cookie）で名寄せ
