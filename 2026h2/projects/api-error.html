APIエラーメッセージの UX 改善

MavHaruMikiko
背景（なぜやるか？）
  • API 予約でエラーが出ると、原因が Traveler に伝わらないまま決済直前で失注している。現場（Sales/CS）発の恒常的な課題。
  • 単発ではなく通年。1〜7月で約 957 件・約 860 万円の機会損失（Comm＝API1予約 平均 9,000円換算）。API 接続 AC の増加で今後さらに増える。
  • 検知・分類は 2025 年に実装済み（Detect）。だが Traveler への伝え方（表示）とその先の動線が弱く、失注が止まっていない。
問課題
  • 原因不明のまま離脱する。エラー時に「なぜ進めないか／次に何をすればいいか」が Traveler に伝わっていない。
  • エラーは2タイプで効く手が違う。①満席・締切＝理由を伝えれば別日程・別時間に自分で切り替えられる（表示で戻せる）／②それ以外（電話番号・設定不備・接続断 等）＝表示だけでは直せず、発生を止める対応が要る。
  • 「表示」が弱く「次の動線」が無い。3層で見ると Detect（済）・Display（不親切）・Remediate（欠け）。文言と、その先の探し直し／代替の動線が足りない。
出典：API Booking Error Problem Map（チケット SYS 関連・1〜7月 distinct・9,000円換算）。
方打ち手方針
  • まず現状を把握する 現行 API・エラータイプ・実際に TR に出しているメッセージを棚卸し（下段 ネクストアクション）。
  • ①表示で戻る：文言を「原因＋次の行動」に 満席なら「満席が理由」＋「別日程を選ぶ」を明確に。まずここを最小限で。
  • ②表示では直せない：次の動線を出す／発生を止める 探し直し・代替の動線で離脱させない。直せない発生要因は Remediate（別トラック・他チーム連携の可能性）。
  • 判断軸は Traveler エラーで止めない・迷わせない・次の一手を出す。
進進め方案（進め方の一例）

ベスト・全てではなく初手のイメージ用。現状把握 → よい UX を検討し直す → 段階で改善。

NA現状の収集・整理
現行 API（GROBIC 等）／API ごとのエラーメッセージ・タイプ／実際に TR に表示中のメッセージ を集めて整理する。
次よい UX を検討し直す
集めた実態をもとに、エラー時にあるべき体験を考え直す。
Phase①文言を親切・丁寧・適切に（最小限）
現行のエラータイプに対し、原因と次の行動が伝わる文言へ。まず着手する最小限。※ 8月ピーク前に効かせたい満席型から。
Phase②UX・動線を改善
別の探し直し動線を出す・提案する等、離脱／停止させず次のアクションを促すメッセージや挙動に。

次ネクストアクション

まず現状把握（NA）から。集めて整理する対象は以下。

対象集める・整理するもの
現行 APIGROBIC 等、接続している API の一覧と特性
エラータイプAPI ごとのエラーメッセージ・エラータイプの種類
実表示メッセージ実際に TR に表示しているエラーメッセージの文言
整理を踏まえて「よい UX」を検討し直し、Phase①（文言改善・最小限）→ Phase②（動線・UX 改善）へ進める。
