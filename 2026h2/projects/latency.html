レイテンシー改善（表示速度をやりきる） 最優先

Pitor
背景（なぜやるか？）
  • 他社と比べた表示速度の遅さが、Veltra サイトの決定的なマイナス要因になっている。ページ遷移・操作のたびの待ち時間が離脱に直結する。
  • 影響が大きいのはモバイル。CVR ボトルネック分析 BN3（Mobile ①→②）は月 2,076K セッション規模の離脱ポイント。
  • 新基盤は「高速・軽量」をコアの価値に据えている。現行側も速度を「やりきる」ことが混在期に効く。
  • 計測タグ・スクリプトの積み重ねも速度を蝕む。ガバナンスの GTM 断捨離と地続き。
問課題
  • カテゴリページ：開くたびにスピナー。表示処理 ≈1.5s の大半が「表示する20件ぶんの後処理」で、検索（Elasticsearch）自体は速い（≈0.17s）。 ・isDynamicPrice が 20 件×フルデータ取得で ≈0.85s（実際に要るのは4フラグだけ）／・getApplicableCoupon を20件ぶん SQL 実行するが、結果はフロントで別 API に上書きされ捨てられている。
  • 予約モーダル：日程・人数・開始時間を変えるたびに再読込（≈0.77s）。getActivityInfo() が1リクエストで9回走る。日程は何度も切り替える前提なので累積でストレスになる。
  • 転送量：重い画像・タグが残っている。853KB の AppsFlyer バナー等。サードパーティタグにも整理余地。
出典：ClickUp UX_DESIGN-167 の実測（起点 URL の1リクエスト）。
方打ち手方針
  • ① 後処理の重さを削る（最大要因・最優先） 必要なデータだけ取る／重複・無駄な呼び出しをやめる／同一リクエスト内の再取得をメモ化する。
  • ② 転送量を減らす 不要なサードパーティタグを減らす・defer する／重い画像を圧縮する。
  • ③ 効果 × 低工数の高いものから着手 S〜M 工数で効くものは即着手。大きいものは効果見積もりを添えて別チケット化。
  • ④ キャッシュ戦略は後段 同一条件の再取得回避は精度とのトレードオフ。上記を実装してから検討する。
バーの長さ＝インパクトの大きさ／着手の優先度。
