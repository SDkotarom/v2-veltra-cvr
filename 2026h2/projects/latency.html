レイテンシー改善（表示速度をやりきる） 最優先

Pitor
背景（なぜやるか？）
  • 他社と比べた表示速度の遅さが、Veltra サイトの決定的なマイナス要因になっている。ページ遷移・操作のたびの待ち時間が離脱に直結する。
  • 影響が大きいのはモバイル。CVR ボトルネック分析 BN3（Mobile ①→②）は月 2,076K セッション規模の離脱ポイント。
  • 新基盤は「高速・軽量」をコアの価値に据えている。現行側も速度を「やりきる」ことが混在期に効く。
  • 計測タグ・スクリプトの積み重ねも速度を蝕む。ガバナンスの GTM 断捨離と地続き。
問課題
  • 表示・操作の遅さがそのまま離脱に。特にモバイルで、読み込みや反応の遅れが取りこぼしになる。
  • 遅さは1箇所にない。サイト全体共通（重い共通スクリプト・画像・計測タグ）／ページ種類ごと（重い一覧生成・データ取得）／個別の操作ごと（変更のたびの再読込）の各レベルに散在する。
  • どこから効くかを決め打ちできない。まず計測して、どのレベル・どの処理で時間が溶けているかを切り分ける必要がある。
方打ち手方針（どう考えるか）
  • ① サイト全体共通で効くもの 全ページに波及。共通スクリプト・計測タグ（GTM 断捨離）・共通画像/フォント・キャッシュ/CDN 方針。効けば一気に全体が速くなる。
  • ② ページ種類ごと カテゴリページ／AC 詳細／予約フォーム等、種類特有の重い処理（一覧生成・データ取得）を潰す。
  • ③ 個別の操作ごと 日程変更・絞り込み等、操作のたびに走る処理を デバウンス／オプティミスティック UI／キャッシュ で軽くする。
  • 各レベル共通の原則 計測して重い原因の順に潰す。低工数 × 高効果から着手し、速い状態を測って保つ。

実実態分析（3レベルで整理）

上の3レベルで「いま分かっていること」と「これから見るところ」を並べる。調査は各レベルとも計測から。

レベルいまの実態・実測これから見るところ
全体共通 GTM・サードパーティタグは既に非同期（影響小）。853KB の AppsFlyer バナー等、重い画像が残る。 共通スクリプト／フォント、CDN・キャッシュ方針、全ページ共通の重い要素。
ページ種類ごと カテゴリページ：一覧生成が重い（filter() ≈1.5s。個別例 UX_DESIGN-167 で実測）。 AC 詳細／予約フォーム／マイページ 等、他のページ種類の重い処理。
操作ごと 予約モーダル：日程/人数/開始時間の変更で再読込（formData() ≈0.77s。個別例で実測）。 絞り込み・ソート・ページング等、頻出操作のたびの処理。
出典：ClickUp UX_DESIGN-167 の実測（カテゴリページ表示・予約モーダル操作）。後回し：同一日程の再選択キャッシュ（速度×精度のトレードオフ）は上記の後に検討。

査現状調査の方法（何に時間がかかっているか）

PageSpeed Insights は入口の1つ。「①どこ・どの操作が遅いか（実ユーザー）→ ②なぜ遅いか（合成計測で内訳を割る）→ ③TTFB が犯人ならサーバ側」の順で掘ると、当てずっぽうにならない。

層手法分かること（＝何に時間がかかっているか）
合成PageSpeed Insights（利用中）Lighthouse スコア＋診断＋一部フィールド(CrUX)。1 URL の総合評価と改善候補の入口。
合成Chrome DevTools（＝検証モード）Network＝ウォーターフォールで TTFB／ダウンロード／待ち時間、どのリクエストが待たせているか・総数・転送量。Performance＝メインスレッド・Long Task・重い JS 関数。Coverage＝未使用 JS/CSS の割合。「何に時間がかかっているか」を割るのはここが本命。
合成Lighthouse CI / CLIPSI と同じ監査を全ページ一括・定点観測。JSON で保存して差分（回帰）を検知。サイト全体を測るならこれ。
合成WebPageTest実回線・地域・実機を指定。フィルムストリップで「見えるまで」を可視化。モバイル×海外回線の再現に最適（本 PJ のモバイル最重視に直結）。
実測CrUX（Chrome UX Report）実ユーザーの Core Web Vitals。CrUX API／BigQuery／Looker Studio ダッシュボード。端末・URL 群別で「実際に遅いページ」を特定。
実測Search Console の CWV レポートフィールドデータで不良 URL 群を抽出（既存の課題資料でも使用）。
実測GA4（MCP 接続可）ページ別の離脱・エンゲージメントと突き合わせて「遅い×離脱」を可視化。※注意：旧「サイトの速度」レポートは廃止。CWV は web-vitals.js を送っていなければ取れない → まず速度系イベントが飛んでいるか確認から。
実測RUM（New Relic Browser／Datadog RUM／Sentry）実ユーザーの LCP/INP/TTFB を継続監視。New Relic APM・Datadog は社内導入済みで活用余地あり。
サーバAPM / CloudWatchサーバ処理時間・遅いトランザクション・どの API が遅いか。TTFB の中身を割る。
サーバCloudFront ログ／ES slow query logキャッシュヒット率（miss 多発＝TTFB 悪化）、検索・一覧生成の遅延クエリ。
サーバサーバサイドのタイミング実測UX_DESIGN-167 でやった isDynamicPrice 0.85s のような処理内訳の計測＝原因特定の核心。
次の一手：PSI の次は Chrome DevTools（Network/Performance）＋ WebPageTest でモバイル回線を再現して内訳を割るのが最短。全ページを継続で見るなら Lighthouse CI、実ユーザーの体感は CrUX／Search Console で裏取り。TTFB が支配的なら APM／CloudFront ログへ。

優着手優先度（Impact × Effort）

「効果が高く工数が小さい」ものから。各施策を ICE ＝ Impact × Confidence ÷ Effort でスコア化し、降順に並べる。まず 全ページ共通で効く × UI を変えない × 低リスク の Quick Win を同時多発で。

0 番目（前提）：着手前に Lighthouse CI / DevTools でベースラインを固定。でないと「効果が高い」を後で証明できない。指標は本 PJ のゴール（表示を◯秒短縮）に紐づける。
番号は下表と対応。左上ほど「小工数で大きく効く」。⑥⑦は効果は大きいが工数大なので別枠で工数確保。
