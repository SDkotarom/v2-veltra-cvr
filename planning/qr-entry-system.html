Executive Summary（結論先出し）

既存QRはコロナ禍急造の限界品で、競合（Klook/KKday）に対し「土俵に乗っていない」。リンクティビティに固執せず、外部の既存QRソリューションを接続して夏の繁忙期前にパイロット導入し、段階的にTraveler体験とPartner業務を改善する。

何がわかったか

  • 現行QRはイベント1人1.5分でパニック、Partner使用は23社で頭打ち
  • Partnerに日次予約一覧ダッシュボードがなく、CSV運用で現場が困難
  • B2B（ANA等）でQR表示できずクレーム → 営業がQRを外す逆行が発生
  • 競合は自社QRを無料提供。Veltraは「土俵不在」で機会を失っている
  • 半年前から議論があったが主導者不在で停滞 → スクワットが拾うべき領域

何をすべきか

  • 外部の既存QRソリューション3〜5社を比較し、ベンダー接続でMVPを最速導入（最速は見込み、Phase 0で再確認）
  • Phase 1は自社OTA経由予約に絞ってQR表示、Partnerは予約者リスト＋スキャンの2画面から開始（影響範囲を最小化）
  • B2B（ANA等）経由予約のQR組込はPhase 2の検討範囲とする
  • パイロット施設（サビチ鍾乳洞ほか）で運用検証 → 学習サイクルを最速で回す
  • リンクティビティとの棲み分けは執行役員Lvの議論待ちのため、依存せず別走
  • 開発リソースはスクワット別建てで確保（Kotaro が外中さん含めて調整）
判断ゲート: Phase 1（パイロット）終了時に「Partner運用負荷が現行を上回らない」「Travelerチェックイン体験が現行より改善」の2点をパイロット施設で評価。両方クリアでPhase 2（横展開）へ進む。B2B（ANA等）経由予約の組込はPhase 2の検討範囲とし、Phase 1ゲートには含めない。

01ソリューション方針

「自社でゼロから作る」「リンクティビティに乗る」「外部既存ソリューションを接続する」の3択を比較し、初動として外部接続を選択する根拠を示す。

3つの選択肢の比較

メリット
デメリット
A. 自社開発
仕様の自由度・データ保有・将来の事業資産化が最大
開発工数が読めず、半年前から動いていない過去の経緯あり。夏には絶対間に合わない
B. リンクティビティ接続
社内グループで意思疎通しやすく、既に仕組み保有
3〜3.5%の重量課金、Veltraコミッションを侵食。両社の事業思惑が一致しないため案件が進まない過去あり
C. 外部ベンダー接続 採用
あり物が市場に多数。手数料の構造はBと同等以下にできる可能性。逆忖度がなく開発が止まらない。今夏リリースが現実的に狙える（最速見込み）
仕様の制約あり。将来的にスイッチ・自社化が必要になる可能性。「最速」は見込みであり、実装スピードはベンダー依存・Phase 0の選定で再確認する前提
Cを選ぶ理由: 「綺麗な自社クローズドシステムを最初から持つ必要はない。まず外部接続で動かし、ノウハウが溜まったら自分たちのソリューションに切り替えればよい」（打合せでの合意）。Phase分割の理由 = 学習サイクルを最速で回す。

採用判定の3条件（外部ベンダー選定基準）

必須
① API連携の柔軟性

Veltra予約データを取り込み、QR発行・利用済みステータス更新が双方向APIで可能。CSV運用に逆戻りしない構造。

必須
② 手数料が薄い

トランザクション課金または定額。リンクティビティの3%相当と同等以下を目安。Veltraコミッションを侵食しない設計。

必須
③ Partner向けスキャン画面

スマホブラウザでQR読取＋利用済みボタンが動く。アプリ強制ではないこと。施設のIT非習熟Partnerでも使える。

推奨
④ B2B予約フローへの対応

ANAなどB2B経由予約でもQR生成が成立。Travelerのチケットメール・PDFバウチャー両方にQR埋め込み可能。

推奨
⑤ データエクスポート

チェックインログをBigQuery等にエクスポートできること。将来のCRM・データビジネスへの素地。

推奨
⑥ 多言語UI

Traveler/Partner両方の画面がEN/JP対応。インバウンド・将来の海外展開を阻害しない。

02ユースケース・要件

「誰のどの困りごとを解くのか」をTraveler / Partner / Veltra の3視点で整理し、MVP に含めるべき要件と Phase 2 以降に回す要件を切り分ける。

3視点のユースケース

Traveler

困りごと当日紙バウチャー or アナログ提示で時間がかかる。B2B経由予約ではQRが出ず会場でクレームになる。

解決まず自社OTA経由の予約に対して、マイページ・メール・PDFバウチャーでQRを表示。会場でスマホをかざすだけで入場完了。B2B経由はPhase 2で組込検討。

MVP必須自社OTA経由予約のマイページ・予約完了メールにQR表示。

Phase 2+B2B（ANA等）経由予約でのQR生成、Apple Wallet/Google Wallet保存、多言語UI。

Partner

困りごと当日の予約者リストがCSV手元落としでしか見られない。スマホで「もぎる/利用済み」の操作機能がなく、現場運用に耐えない。

解決スマホブラウザで日付別の予約者リスト＋QRスキャナが動く。スキャンすればその場で利用済み更新、二重入場を防ぐ。

MVP必須当日の予約一覧（日付・時間・人数・氏名）／QRスキャナ／利用済みステータス更新。

Phase 2+来場リアルタイム集計、当日のキャンセル/変更対応、入場時写真撮影・本人確認連携。

Veltra（事業基盤）

困りごとパートナー営業時に「QR提供できる/できない」で勝てない。B2BパートナーはQR欠如を理由に外す。チェックインデータが手元に残らない。

解決営業の武器としてQR標準提供。チェックイン実績を蓄積し、リテンション施策や直販施設データ活用の素地を作る。

MVP必須Partner営業時の提供メニューにQR追加／チェックインログのDB保存。

Phase 2+BigQueryエクスポート、CRM連携、リテンション分析、データビジネス検討。

03ロードマップ・スケジュール

Phase分割の理由: ① Phase 0は意思決定の塊で独立、② Phase 1は学習サイクルを最速で回すため最小単位、③ Phase 2 以降は Phase 1 の判定ゲートを通過してから着手し過剰投資を避ける。

Phase 0整理・準備〜5月末（2週）

  • 本ドキュメントを Kinoshita・Nishioka にレビュー依頼 → 修正
  • 外部QRベンダー3〜5社のショートリスト作成（API連携・手数料・スキャン画面・B2B対応で評価）
  • パイロット候補施設のヒアリング（サビチ鍾乳洞ほか）→ 現状の業務フロー把握
  • 開発リソース確保の再相談（Makino × 外中さん）／ スクワット内別建てを正式決定
  • リンクティビティとの「別走」方針を関係者に説明（執行役員Lvの議論は別線）
分割理由: 意思決定とリサーチに集中し、後工程の手戻りを避けるため。

Phase 1MVP導入・パイロット6月〜7月（〜夏繁忙期前）

  • 外部ベンダー1社決定・契約／開発接続着手
  • Traveler側: 自社OTA経由予約を優先し、マイページ・予約完了メールにQR表示を実装（影響範囲を最小化）
  • Partner側: スマホブラウザのスキャン画面＋予約一覧の最小限UI
  • パイロット施設1〜2社（サビチ鍾乳洞ほか）で運用開始
  • 運用ログ・クレーム・改善要望を週次で収集 → 学習サイクル開始
分割理由: 学習サイクルを最速で回す。夏繁忙期の実トラフィックで検証することで、机上想定では見えない課題を抽出。B2B等の組込はPhase 2に回し、Phase 1は影響範囲を最小に絞ることで繁忙期前リリースの確度を上げる。

Phase 2横展開・武器化8月〜10月

  • Phase 1 の判定ゲート（2点）を通過したら着手（未達なら設計見直し）
  • パートナー10〜20社まで段階拡大
  • B2B（ANA等）予約フローへのQR組み込み検討・実装
  • Partnerダッシュボード強化（リアルタイム集計・キャンセル対応）
  • Wallet連携・利用ログのBigQueryエクスポート
分割理由: Phase 1 でベンダー仕様・運用負荷が見えてから、横展開の投資判断をする。

Phase 3事業資産化・新基盤統合11月以降

  • 新基盤（Jasonさんチーム）への統合視野
  • CRM連携・リテンション分析の運用化
  • 多言語対応（ENサイト統合）
  • 自社化（外部ベンダースイッチ）の意思決定
  • データビジネスとしての位置づけを明確化
分割理由: 新基盤の開発進捗との依存解消。Phase 2 までで蓄積したノウハウを自社資産に転換する判断を独立で行う。
Phase 1 → Phase 2 の判定ゲート: ① Partner現場の運用所要時間が現行（紙バウチャー・CSV）を上回らない／② Travelerチェックイン体験が現行より改善（パイロット施設で1人あたり時間計測） — 2点クリアで「横展開」を意思決定。
※ B2B（ANA等）経由予約のQR組込はPhase 2の検討範囲（Phase 1では自社OTA経由を優先）。

本施策はCVR3軸（取りこぼし防止／迷わず買う／滞在中プラスアルファ）の外にある「予約後体験・パートナーソリューション・リアルサービス事業」軸。CVR施策とは別建てで管理することを明示する。

本来の位置づけ：3つの戦略意義（Nishioka視点）

事業
リアルサービス事業の第一歩

OTAではなく「事業者の業務効率化」を提供する立場へ。グローバルOTAに対する日本企業としての差別化。

資産
顧客データ蓄積の素地

施設の予約管理を担うことで来訪者データが手元に残る。CRM・将来のデータビジネスへの第一歩。

営業
「ありとキリギリスのあり」戦略

大手（USJ等）は取れないが、困っている小さな施設をたくさん助けることで切っても切れない関係値を全国で作る。

06背景・現状課題（なぜやるか）

2026-05-18の打ち合わせで共有された現状認識と課題。

現行QRシステムの課題（Kinoshita報告）

  • 急造の限界: コロナ禍にイベント対応で無理くり作られた仕組み。大型イベントで1人当たりチェックインに1分半かかり、現場がパニックになる事例あり
  • Partner普及の停滞: 現使用は23 Partnerに留まる。ダッシュボード機能の欠如とCSV運用の限界が普及を阻んでいる
  • スマホ操作機能の欠落: 「もぎる」「利用済みボタン」のオペレーションがなく、Partner現場で実用に耐えない
  • B2B（ANA等）でのコンプレイン: QR表示できないことが理由でQRオプションを外す逆行が発生

競合との差（Nishioka報告）

  • Klook / KKday は自社販売分のQRを無料で標準提供している
  • 「グローバルOTAは当たり前の土俵に乗っているが、Veltraはその土俵にも載っていない」状態
  • ただし、IT非習熟のPartnerに対しては日本語サポートのあるVeltraに優位性があり得る

リンクティビティとの関係（背景）

既存の仕組みリンクティビティはQRシステムを保有しているが、活用案件が今までなし
手数料構造リンク経由で導入すると3〜3.5%の手数料が発生し、Veltraコミッションを侵食する（例: 15%契約だと実質12%に）
事業の思惑差リンクは自社直販サイトをPartnerに使ってもらいたい。Veltraも直販したい。利害が一致しない
領域の棲み分けリンク = 交通・入場DX。Veltra = アクティビティ。被る領域もあり、現場では明確な答えが出ていない
過去の議論半年前に同様の議論があったが、主導者不在で停滞

パイロット候補：石垣島サビチ鍾乳洞の事例

現状: 観光客がみんな行く施設ではないが、Veltra営業が契約を取れた。現状は現金払い ＋ Veltra紙バウチャー提示というアナログ運用。券売機を撤去し、Veltraの QR を置くだけで業務改善に直結する成功モデルになり得る（Kinoshita）。
次の意思決定ポイント（次回MTGで合意したいこと）
  1. Phase 0 着手の正式合意（スクワット別建てリソース、外中さん含めた相談を経て）
  2. 外部ベンダーのショートリスト基準（API・手数料・B2B対応・データエクスポート）
  3. パイロット施設の優先順位（サビチ鍾乳洞 + α）
  4. リンクティビティとの「別走」方針を執行役員Lvで認知させる動き出しの主管
  5. CVRプロジェクトと本施策の管理ラベル分離の運用合意
