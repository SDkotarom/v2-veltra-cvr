SECTION 02
レコメンドロジック詳細 — Brazeで実現する方法
「どんなレコメンドを、どういう条件で、どう表示するか」を全て具体化。レコメンドシステムは作らず、Brazeのカスタム属性とセグメントだけで実現する。
⚙️
本施策はMLレコメンドではない。Brazeの標準機能（カスタムイベント／カスタム属性／セグメント／Content Cards／Liquidテンプレート）だけで動作するルールベース＋個人属性のハイブリッド設計。
A. DATA COLLECTION
ステップ1：Brazeに送る3つのイベント
1
ACページ閲覧時
ACページが表示されたら、AC情報をパラメータ付きでBrazeに送信。
braze.logCustomEvent("viewed_ac", {
  ac_id, ac_name,
  ac_thumbnail_url,
  ac_price, ac_url,
  ac_rating, area
})
2
カレンダー開示時
既存GTMの view_calendar イベントをBrazeにも送信開始。AC情報を含める。
braze.logCustomEvent("view_calendar", {
  ac_id, ac_name,
  ac_thumbnail_url,
  ac_price, ac_url
})
3
購入完了時
予約完了時に購入情報を送信。購入履歴ベース配信（カードD）で活用。
braze.logCustomEvent(
  "ecommerce_purchase", {
  ac_id, area, category,
  purchase_at
})
Braze側で起こること：これらのイベントを受信するたび、Braze内部でユーザー属性が自動更新される。例えば viewed_ac 受信時は last_viewed_ac_1_* 属性に最新ACを保存し、古い値は last_viewed_ac_2_* → last_viewed_ac_3_* へとシフトする（Brazeの「Update User Attribute via Event」アクションで設定）。
B. CARD SPECIFICATIONS
ステップ2：4つのカードの詳細仕様
どうやって表示する AC を選ぶか

閲覧履歴		 Traveler が直近に見た 3 件 新しい順（時系列）。Braze の last_viewed_ac_1/2/3_* をスライド更新するだけ。「見た回数が多い順」ではない
CARD B
エリア人気		 そのエリアの「ルールベース上位 AC」5件 3条件のAND で月次バッチ自動選定：①直近30日 page_view 上位／②⭐ 4.0 以上＆体験談 10件以上／③営業中。個人の視聴回数ベースでは動かない。出し分けは「どのエリアのリストを見せるか」だけ（ハワイ閲覧者→ハワイリスト 等）
CARD C
カレンダー離脱		 Traveler がカレンダー開いたが買わなかった、その AC Traveler のリターゲット。48 時間以内に view_calendar 発火＋未購入のとき、その AC をそのまま再表示する

購入履歴ベース		 過去に購入したエリアの「ルールベース上位 AC」 過去購入エリアに対する Card B と同じ自動選定（3条件AND）。トリガーは ecommerce_purchase 受信で last_purchase_area 属性が立っている Traveler。「前回ハワイで購入したあなたへ」のような訴求
ポイント：個人の視聴を使っているのは カード A（時系列）と C（リターゲット）のみ。B は「ルールベースで全ユーザー共通の人気上位5件」をエリアごとに自動選定（GA4 + 在庫DB の月次バッチ）。視聴回数 → スコア化 → レコメンドエンジン的な個人最適化はこの段階では入れていない（外部レコメンド API 連携の領域）。

AC 選定ロジック

② 品質条件：⭐ 4.0 以上 ＆ 体験談 10件以上
③ 販売状態：営業中（販売停止・季節終了・天候停止は除外）

「人気」定義の A/B 検証
案A（page_view 上位＝注目）／案B（購入数上位＝実売）／案C（wishlist 追加上位＝欲しがられている）を Braze ダッシュボード上で並行検証。初期は案A、結果を見て切替

同時に複数カードが発火した場合の並び順
順 カード なぜこの順番か
1C カレンダー離脱カレンダーを開いて 48h 未購入＝「もうすぐ買いそう」シグナルが最強。最上部に置けば取りこぼし回収
2D 購入履歴ベース過去にどこかで買った経験＝支払い意欲・サイト信頼が確認済み。リピート訴求の効率が高い

5フォールバック上記いずれも発火しない時の汎用「全体人気 AC」
Braze 側の設定：各 Content Card に「priority（整数）」を割り当て（例：C=10／D=8／A=6／B=4／fallback=2）。複数カードが同じユーザーに該当した場合、Braze SDK が priority の高い順に並べてアプリ/サイトに返す。Braze ダッシュボードで数字を変えれば順番もリアルタイムで切替できる（A/B テストで順番違いも検証可能）。

D. PARALLEL A/B TEST
ステップ4：Braze ダッシュボードで A/B を並行運用
⚡
Phase 分割せず、4 カード（A・B・C・D）× 4 エリア（ハワイ・韓国・グアム・タイ）を Day 4 から一斉稼働させ、Braze ダッシュボード上で A/B テストを並行運用する。開発作業は Day 1〜2 の実質 2 日のみ。Day 3 で Braze セットアップを終え、Day 4 から全カード × 全エリア × A/B variant を同時に投入。以降は Braze 内のセグメント・カード・Liquid を編集するだけで複数検証が同時並行で回る。
並行で回す A/B テスト例（Day 4 配信開始時から同時投入）
  • カードA（閲覧履歴）：TOP3 を表示するか／TOP5 を表示するか／「同エリア人気を併記」するか
  • カードB（エリア人気）：初期4エリア（ハワイ・韓国・グアム・タイ）でスタート、稼働後にスポット粒度（30+）を段階追加して並走させ CTR で比較
  • カードC（カレンダー離脱）：コピー違い（「まだ空きあります」/「あと◯日で満席の可能性」）、48h vs 72h のトリガー時間差
  • カード優先度：4カードの並び順（離脱C → 購入D → 履歴A → エリアB）vs（履歴A → 離脱C → 購入D → エリアB）の比較
  • 追加カード D（購入履歴ベース）：初期から仕込んで「前回ハワイで購入したあなたへ」も並行検証（last_purchase_area 属性使用）
Braze で並行運用するメリット：カード・セグメント・テンプレートが独立してるので、複数の A/B を同時に回しても干渉しない。開発を待たずに、データが出た順番に「勝ち variant」を採用してダッシュボードで切り替えるだけ。「順次フェーズ展開」ではなく「全カード並走 + 継続最適化」が Braze 運用の正しい姿。

現状の課題（実画面確認 2026-05-11）
  • 既存メニューはカウント表示のみ。「保存リスト 1」「閲覧履歴 0」のような数字だけで、Traveler がどの AC を見ていたか分からない
  • マイページの「あなたへのおすすめ」はパーソナライズ機能していない。閲覧履歴0でもスパが表示される静的コンテンツ
  • エリアページのメニューに文脈なし。ハワイ閲覧中でも汎用リンクのみ
  • 結果：リピーターは再訪→汎用ページ→記憶頼りの探索→離脱、または長い回遊で失速
