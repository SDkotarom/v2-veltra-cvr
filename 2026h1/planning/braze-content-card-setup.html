START HERE
「特定traveler IDだけにカードを見せる」をどこで担保するかを最初に決めるのが事故防止のコツ。Brazeセグメントで完結させるのが第一候補で、開発工数ほぼゼロ。詳細は SECTION 02 の方式A/B/C比較を参照。
SECTION 02
準備・前提確認（自分側）
開発依頼を出す前にこちらで終わらせるべき 3 ステップ。GTM コンテナ発行・Braze 連携状況の確認・ID 制御方式の決定。
STEP 01
dev環境用のGTMコンテナを発行
自分
目的
prod 用と分離した GTM コンテナを用意する。dev で誤って prod タグを発火させないため。
手順
  • GTM 管理画面で「新しいコンテナ」→ ターゲットプラットフォーム: Web
  • コンテナID（GTM-XXXXXXX）を控える
  • 代替: 既存 prod コンテナに Look-up Variable で dev/prod 切替も可（要相談）
完了条件
コンテナ ID が手元にある／コンテナのワークスペースがアクセス可能
STEP 02
Brazeに traveler_id が届いているか確認
自分
なぜ確認するか
「特定 traveler ID だけにカード表示」を Braze セグメントで完結させるには、traveler_id が custom attribute or external ID として Braze に送信されている必要がある。
確認ポイント
  • Braze Dashboard → User Search で対象 traveler_id でユーザーが見つかるか
  • traveler_id が custom attribute に入っているか
  • 入っていない場合 → アプリ側で braze.getUser().setCustomUserAttribute('traveler_id', xxx) 連携を追加依頼に
STEP 03
ID制御の方式を決める
自分
3つの案
「特定 traveler ID のみコンテンツカードを見せる」をどこで担保するか。後の手戻りを防ぐためここで確定させてから依頼を出す。
A
Braze セグメントで対象を絞る
対象 traveler_id でセグメント作成。マーケが Dashboard で完結。フロント実装ゼロ。前提: traveler_id が Braze に送られていること（STEP 02 の確認結果次第）。
第一候補
B
ページ側で ID 判定 → 呼ぶ/呼ばない
toggleContentCards() 自体を条件付きで実行。シンプルだが、ID 変更ごとに開発デプロイが必要で運用負荷が高い。
A が無理ならコレ
C
filterFunction で extras と照合
カードの KVP target_traveler_id とログイン中 ID 一致時のみ表示。複雑で運用が事故りやすい。
非推奨
SECTION 03
開発依頼 — GTM導入と企画ページ設置
エンジニアに渡す 2 件のチケット。STEP 04・05 は GTM 導入、STEP 06〜08 は企画ページ＋メニュー導線。
REQUEST 01 — GTM INTEGRATION
依頼① dev環境にGTMを組み込む
STEP 04
dev環境の全ページにGTMタグを設置
エンジニア
依頼内容
  • スニペット1: <head> できるだけ上部
  • スニペット2: <body> 開始直後
  • prod用GTMタグがdevで発火しないこと（環境分離）
渡す情報
dev用コンテナID（GTM-XXXXXXX）。Google公式どおりの2スニペット方式。prodと同じテンプレ位置に入れるのがベスト。
STEP 05
dataLayer に必要変数を積む
エンジニア
なぜ必要か
GTM ロード前に Push してもらえば、Braze SDK 初期化に traveler_id を渡せる。これが無いと方式 A（セグメント制御）が動かない。
実装例
// ログイン後ページのGTMより上で実行 window.dataLayer = window.dataLayer || []; window.dataLayer.push({ user_id: "<internal user id>", traveler_id: "<traveler id or undefined>", login_status: "logged_in" // or "guest" });
完了確認
  • GTM Preview / Tag Assistant が dev 環境で接続できる
  • window.dataLayer が初期化されている
  • ログイン後ページで traveler_id が積まれている
REQUEST 02 — PLANNING PAGE & MENU LINK
依頼② 企画ページとメニュー導線を設置
STEP 06
dev環境に企画ページ本体を配置
エンジニア
参考レイアウト
personalized-header-menu.html 相当。ページ内に Content Card 描画用コンテナ #braze-content-cards を用意する（Silver Egg レコメンドの直前に配置）。
HTML
<section class="braze-test-section"> <div id="braze-content-cards"></div> <!-- Silver Eggレコメンドの直前に配置 --> </section>
STEP 07
GTMカスタムHTMLタグでContent Cards発火
エンジニア
方針
企画ページのURLパスで発火するトリガーを設定し、以下のスニペットを実行。Default UI をそのまま使用することで Analytics は自動取得（手動 log 実装ゼロ）。
実装例
// GTM Custom HTML Tag window.addEventListener('load', function() { if (!window.braze) return; // 初回訪問でも即同期したいので明示リフレッシュ braze.requestImmediateDataFlush(); braze.requestContentCardsRefresh(); // 指定DOMにContent Cardsを描画 var mount = document.getElementById('braze-content-cards'); if (mount) braze.toggleContentCards(mount); });
STEP 08
ヘッダーメニューに導線を追加（表示制御込み）
エンジニア
依頼内容
ログイン後ヘッダー（またはマイページ）に新規リンクを追加。方式 A 採用時はリンク自体は全ユーザーに見せて OK（Braze 側で配信制御）。完全に隠したい場合は許可リスト判定。
パラメータ
  • 表示文言: {{要相談・例: "会員特典テスト"}}
  • リンク先: STEP 06 のページ URL
  • 表示条件: ログイン済み
  • 追加条件（方式 B 採用時）: traveler_id ∈ 許可リスト
完了確認
  • 許可ユーザーでログイン → 新規リンク表示 → 遷移 → #braze-content-cards 内にカード描画
  • window.braze が初期化済み
  • 非該当ユーザーにはカード非表示（リンク自体の出し分けは方式による）
SECTION 04
Brazeキャンペーン設定（マーケ）
開発依頼と並走可能。Content Card キャンペーンを作成し、セグメント・KVP・有効期限を仕込む。
STEP 09
Content Cardキャンペーン作成
マーケ
手順
  • Messaging → Content Cards → New Campaign
  • Card Type: Classic / Captioned / Banner（テストは Classic が楽）
  • セグメント: traveler_id = 許可リスト（方式 A）
  • Trigger: Start Session In Any App
  • "no re-eligibility" にチェック（初回訪問でも確実に表示）
STEP 10
有効期限（Expiration）を必ず設定
マーケ
注意
キャンペーン終了日とカード有効期限日は別物。両方設定する。
設定項目
  • Campaign Duration: Start / End Time（配信ウィンドウ）
  • Removal Conditions → Expiration (Time in Feed): 最大 30 日
  • 1 カードあたり 2KB 制限・Feed 内 100 件上限を意識
CAUTION
キャンペーン終了日 ≠ カード有効期限日。キャンペーンが終了しても、すでに配信されたカードは Feed 内に Expiration 設定の日数だけ残り続ける。両方を意識的に設定しないと「終了したはずなのにカードが消えない」「終了前に消えた」が起こる。
SECTION 05
疎通テスト・Currents記録の確認
Default UI 採用のため Impression / Click / Dismiss は SDK が自動 log する。手動実装は不要。
STEP 11
許可ユーザーで端末から実機検証
検証
チェック項目
  • 許可 traveler_id でログイン → 企画ページにアクセス
  • Content Card が描画される / クリックで url 遷移する / Dismiss で消える
  • DevTools で braze.getCachedContentCards() がカード配列を返す
STEP 12
Braze Currentsで4イベント記録を確認
検証
確認対象
  • users.messages.contentcard.Send
  • users.messages.contentcard.Impression
  • users.messages.contentcard.Click
  • users.messages.contentcard.Dismiss
SECTION 06
参考資料
配信シーケンス・カスタマイズ 3 レベル・用語集。チケット起票時の補助資料として。
A. DELIVERY SEQUENCE
配信・記録のシーケンス
Braze Content Card がクライアントに届いて Currents に記録されるまで
01 Braze Server
キャンペーン配信日時が到来
02 Braze Server
Content Card を作成
03 Braze Server
Send イベントをログ
04 App / Web
セッション開始 or requestContentCardsRefresh() でカードを同期取得
05 App / Web
カードがクライアントに配信される
06 User
カードを閲覧
07 Braze SDK
Impression を自動ログ（Default UI 時）
08 User
クリック / Dismiss
09 Braze SDK
Click / Dismiss を自動ログ
NOTE
データ送信間隔。Web SDK は 10 秒間隔＋セッション終了(30 分経過時)。即時に送りたい場合は requestImmediateDataFlush() を呼ぶ。
B. CUSTOMIZATION LEVELS
カスタマイズ3レベル比較
レベル やること 開発工数 Analytics 今回のテスト
Default そのまま toggleContentCards() 呼ぶだけ 最低 自動 採用
Style 色/フォントなど CSS のみ上書き 小 自動 —
UI カードの HTML/セルを差し替え 中 自動 —
UX SDK UI を使わず payload だけ受けて自社UI 大 手動実装必須（Impression / Click / Dismiss） —
CAUTION
UXカスタマイズの罠。Braze の用意した UI を使わない場合、logContentCardImpression / logContentCardClicked / logContentCardDismissed / logContentCardsDisplayed を自前で呼ばないと Currents 記録がゼロになる。本格導入時の罠。
C. GLOSSARY
用語集
braze.toggleContentCards(parentNode, filterFn)
指定DOMにContent Cardsフィードを描画/破棄するWeb SDKメソッド。parentNode省略時は右サイドバー。
braze.requestContentCardsRefresh()
任意のタイミングでサーバから最新カードを再取得する明示同期。
braze.requestImmediateDataFlush()
10秒バッチを待たず、即時にイベントをBrazeへ送信する。
extras (KVP)
Dashboardで設定するKey-Value Pair。カード分類・遷移先制御・複数フィード分割などに使う。
no re-eligibility
同一ユーザーへの再配信抑止オプション。初回セッションでカード重複表示を避ける。
Send / Impression / Click / Dismiss
Currentsで取得できる4イベント。Default UIは自動、カスタムUIは手動log必須。
Expiration (Time in Feed)
配信後カードがFeedに残る期間。最大30日。キャンペーン終了日とは別軸。
Card Properties
idString / url / imageURL / title / cardDescription / extras / viewed / pinned ほか。extrasでKVPアクセス。
