# 表示速度改善の効果指標：設計の叩き台

目的：CVR だけでは、表示速度の改善が効いたかどうかを判断できない。離脱の減少、回遊の増加など、CVR の手前の段階の指標で、効果を確認できるようにする。
この文書は、鉄平さんとの方針のすり合わせ用。数字は、特記がなければ GA4（Property 347074845）の、2026-09-23 から 10-20 の値。

## 1. 考え方

- 表示が速くなると、ユーザーの行動は、次の順に変わると想定する。CVR は最後の段階で、動きが小さく、ほかの要因（季節、広告、価格）に埋もれやすい。
- 手前の段階の指標ほど、改善の影響を受けやすく、短い期間で変化が見える。
- ただし、手前の段階の指標が動いても、CVR が動くとは限らない。両方を並べて見る。

| 段階 | 見るもの | 例 |
|---|---|---|
| 0. 速度そのもの | 速さが変わったか | 実ユーザーの最初の応答時間、手計測の待ち時間 |
| 1. 直後の行動 | そのページで、すぐ離れたか | 1ページで終わった割合、操作した割合 |
| 2. 次の行動 | 次のページに進んだか | 一覧から商品ページへの到達 |
| 3. 回遊の深さ | どれだけ見たか | 1セッションあたりの閲覧数、商品ページの閲覧数 |
| 4. 予約に近づく行動 | 予約の手前まで進んだか | カレンダー表示、予約フォーム表示 |
| 5. 結果 | 予約が増えたか | CVR |

## 2. 対象ごとの指標

GA4 の、今あるイベントとカスタムディメンションだけで出せるものを、先に挙げる。取得できると確認したものは「確認済み」、確認していないものは「未確認」と書く。

### カテゴリー（一覧）

| 段階 | 指標 | 出し方 | 状態 |
|---|---|---|---|
| 0 | 最初の応答時間、絞り込みの待ち時間 | 実ユーザー値（CrUX）、手計測 | カテゴリーの CrUX は、収集対象への追加が済んでいるか未確認。手計測は可能 |

## 3. 速さと行動を結びつける方法

「速くなった」と「行動が変わった」を、つなぐ方法は2つある。

1. **改善の前後を比べる。** リリース日の前後で、段階1〜4の指標を比べる。
   - 比べる期間は、同じ曜日の構成にそろえる。
   - 何も変えていないページ（対照）も同時に出す。季節や広告の影響を、除くため。
   - 変化が「ばらつきの範囲」を超えたときだけ、変わったと言う。PSI の判定と同じ規則で、日ごとの標準偏差を基準にする。
2. **速度の段階ごとに行動を比べる。** 同じ期間の中で、速かったセッションと遅かったセッションで、離脱や回遊がどう違うかを見る。
   - 実ユーザーの速度を、GA4 のイベントとして送る必要がある（web-vitals タグ、UX_DESIGN-300）。タグの公開は、まだ済んでいない。
   - 速いセッションは、もともと回線や端末が良い。その偏りがあるので、単純な比較は、原因を示さない。

## 4. 注意点

- **CVR が動かなくても、効果がないとは言えない。** 手前の指標が動いたかを、先に見る。
- **指標の定義を先に決める。** 離脱の意味が、決まっていない。
  - 案A：エンゲージメント率の逆（GA4 標準）。セッション単位。
  - 案B：そのページで、セッションが終わった割合（ページ別の離脱率）。GA4 の Data API に標準の指標があるかは、未確認。探索レポートか BigQuery エクスポートが必要かもしれない（BigQuery の有無も未確認）。
- **ほかの要因。** 同じ時期の、ほかのリリース、広告、キャンペーン、季節。一覧にして、前後の比較の注記に入れる。
- **件数の少ないイベント。** `load_more`、`filter_apply` などは、件数が少なく、日ごとに比べるとばらつく。

## 5. 鉄平さんとすり合わせたいこと

1. 成功の定義：カテゴリーと検索で、どの指標が、どれだけ動いたら、効果があったと言うか。
2. 離脱の定義：案A と案B のどちらか。
3. 計測の追加：不足するイベント（カテゴリーの絞り込み、検索結果の表示など）を、追加してよいか。追加するなら、誰が、いつまでにやるか。
4. 評価の期間と比べ方：前後の何週間を比べるか。対照のページは、どれにするか。
