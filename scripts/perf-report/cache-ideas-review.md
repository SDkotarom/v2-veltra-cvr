# カテゴリー・検索の改善案：メリット・デメリットの整理

出典：Suki さんの Slack 投稿（#proj-web-performance、10/14 のスレッド、10/20 12:16）。日本語化と整理は牧野側。
数字のうち、Suki さんの見積もりと、あとで確認が必要なものは、そのように書いている。

## 前提

- 対象：カテゴリーページと検索ページ（Suki さんが「効果的に改善できる」とした2ページ）
- 目的：ユーザーが体感する待ち時間を短くする（ローディングのリング回転、最初の応答までの時間）
- 関連する実測
  - 検索の実ユーザーの最初の応答（TTFB）：5.5 秒（10/3 の週）
  - カテゴリーの絞り込み：平均 1.82 秒から 0.97 秒（UX_DESIGN-309、手計測 10 回）
- 現状の仕組み（Suki さんの説明）
  - カテゴリー1ページ目：最新のデータを取りにいき、30 分単位の区切りでキャッシュ
  - カテゴリー2ページ目以降：キャッシュなし
  - カテゴリーの絞り込み結果：キャッシュなし（UX_DESIGN-309 の対象は、絞り込みなしの1ページ目だけ）
  - 検索ページ：ページキャッシュがあれば、それを出す。なければ、サーバーが結果を取るまで待つ
  - 検索 API：検索結果を 1 時間だけキャッシュ

## カテゴリー

### C1：1ページ目を、24 時間のページキャッシュにする

- 現状：1ページ目は最新のデータを取りにいき、30 分単位の区切りでキャッシュしている
- 案：ページキャッシュを 24 時間にする。Sightseeing_Tour のカテゴリーページ（`/jp/ctg/160126:Sightseeing_Tour/`）が、すでに同じ方式
- メリット
  - ローディングのリングが出ない
  - ページが速く表示される
  - 保存する量は、大きくは増えない（未確認）
- デメリット
  - 古いデータが、最大 24 時間出る可能性がある（Suki さんの例：特別セール）
- 確認したいこと
  - 一覧に出る価格・在庫・売切れ・セール表示が、24 時間古くなってよいか（牧野側は未確認）
  - 今のカテゴリーのうち、どのページが、すでにページキャッシュで、どのページがまだなのか
  - キャッシュを消す操作が必要になる場面（商品の公開停止など）の扱い

### C2：2ページ目以降を、30 分単位でキャッシュする

- 現状：2ページ目以降は、キャッシュなし
- メリット：キャッシュが温まっていれば、読み込みが速くなる
- デメリット
  - 容量を使う。全カテゴリーのページを保存すると、本番で 1.6GB を超えるという、ざっくりした見積もり（Suki さん）
  - 2ページ目以降を見るユーザーの割合が分からない（牧野側は未確認）。効果の大きさが読めない
- 確認したいこと
  - memcache の、今の使用量と、空き容量
  - 1.6GB を増やしても問題ないか

### C3：絞り込み結果を、30 分単位でキャッシュする

- 現状：絞り込み結果は、キャッシュなし
- メリット：キャッシュが温まっていれば、速くなる
- デメリット
  - 絞り込みの組み合わせが多い。キャッシュに当たる割合が、どれだけ高くなるか分からない
  - memcache の容量を、かなり使う
  - Suki さんの 9/22 のコメントでも、全部の組み合わせは保存できないという趣旨
- 範囲を狭める案（Suki さん）
  - GA で、よく使われる絞り込みを調べ、それだけを対象にする
  - 日付が 1 日だけの検索だけを、対象にする
- 確認したいこと
  - よく使われる絞り込みの上位が、全体の何割を占めるか（GA4 で集計できるかは未確認）
  - 範囲を狭めた場合の、保存量の見積もり

## 検索

### S1：枠を先に出し、結果は準備ができてから描画する

- 現状：ページキャッシュがあれば、それを出す。なければ、サーバーが結果を取るまで待つ
- 案：HTML のページを先に出し、検索結果のカードの場所には、仮の枠を置く。結果が揃ったら描画する
- メリット：最初の応答までの時間（TTFB）が短くなる
- デメリット
  - 表示のずれ（CLP と書かれているが、CLS のことか未確認）に影響する可能性がある
  - 仮の枠のデザインを決める必要がある
- 確認したいこと
  - 検索 API の改修が要る点（peregrine-api。Suki さんが変更でき、PR は Andy さん（KL チーム）に出す、という 10/14 のコメント）
  - ユーザーにとって、枠だけが先に出る状態が、どう見えるか（プロダクト側の判断）

### S2：検索ページと filter_kw() の ajax を最適化する

- 現状：検索 API は、結果を 3 秒未満で返す。それでも TTFB は 5 秒を超える。検索ページか filter_kw に、余計な処理があると疑っている（Suki さんの推測）
- メリット：原因が見つかれば、キャッシュの有無に関係なく、速くなる
- デメリット：まだ原因が特定できていない。まず、処理の内訳を測る必要がある（UX_DESIGN-406 の計装と同じ方向）
- 確認したいこと：処理の内訳を測る方法と、本番に入れてよいか

### S3：よく検索されるキーワードを、定期実行で先にキャッシュする

- 現状：検索 API は、検索結果を 1 時間だけキャッシュする
- 案：定期実行のタスクを作り、よく検索されるキーワードのキャッシュを、常に温まった状態にする
- メリット：よく検索されるキーワードは、いつでも速くなる
- デメリット
  - 珍しいキーワード、初めてのキーワードには、効かない
  - 定期実行の仕組みを、新しく作る必要がある
- 確認したいこと
  - よく検索されるキーワードの上位が、全体の何割を占めるか（GA4 で集計できるかは未確認）
  - 定期実行を動かす場所と、運用の担当
