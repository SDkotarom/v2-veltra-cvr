# アクセス制御（パスコードゲート）

このサイトは社外非公開です。`middleware.js`（Vercel Edge Middleware）が
**すべてのリクエストをエッジで受け止め**、有効な署名付き Cookie を持たないものを遮断します。
Vercel の無料（Hobby）プランで完結し、Google / Okta は一切経由しません。

---

## 1. 仕組み

```
リクエスト（HTML / JSON / 画像 すべて）
   ↓
middleware.js
   ├─ Cookie v2_access を検証（HMAC-SHA256 署名＋有効期限）
   │    有効   → そのまま配信
   │    無効   → ページ遷移なら /login.html?next=… へ 302
   │             fetch / curl なら 401（中身を返さない）
   └─ /api/login・/api/logout・/api/session をこのファイル内で処理
```

- 保護対象は**全パス**。`login.html` と `favicon.ico` のみ認証前に到達できる
- 静的な JSON（`summary-data.json` など）も同じゲートを通るので、URL を知っているだけでは取得できない
- Cookie は `HttpOnly` / `Secure` / `SameSite=Lax`。JS から読めず、署名があるため偽造・有効期限の書き換えもできない
- 有効期限は **60日**。一度入れば関係者は以後ノークリックで閲覧できる

## 2. 初期セットアップ（Vercel ダッシュボード）

**Settings → Environment Variables** に以下2件を追加する（Production / Preview の両方）。
どちらも**リポジトリには絶対に置かない**。

| 変数名 | 用途 | 生成方法 |
|---|---|---|
| `ACCESS_PASSCODE` | 関係者に共有するパスコード | 下記コマンド、または覚えやすい長めの文字列 |
| `ACCESS_SECRET` | Cookie 署名用の秘密鍵（共有しない） | 下記コマンド必須（32文字以上のランダム） |

```bash
# パスコード（共有する側）
openssl rand -base64 12 | tr -d '/+=' 

# 署名鍵（誰にも共有しない）
openssl rand -base64 48
```

設定後に再デプロイすると有効になります。
**未設定のままだとサイト全体が 503 で止まります**（fail-closed。設定漏れで中身が漏れることはありません）。

## 3. 関係者への共有方法

Squad の Slack 非公開チャンネルに、次のリンクを**ピン留め**します。

```
https://v2-veltra-cvr.vercel.app/login.html#p=<ACCESS_PASSCODE>
```

- 開くだけで自動ログインし、そのままポータルが表示されます（入力の手間ゼロ）
- `#` 以降（フラグメント）はブラウザからサーバーへ送信されないため、
  Vercel のアクセスログや外部サイトへの Referer には残りません
- ログイン後は URL から自動的に取り除かれます
- 以後60日はブックマークから直行できます

パスコードを直接伝えたい場合は、通常どおり `https://v2-veltra-cvr.vercel.app/` を開いて
ログイン画面で入力してもらう形でも動きます。

## 4. 失効・ローテーション

| やりたいこと | 操作 |
|---|---|
| パスコードだけ変更（既存ログインは維持） | `ACCESS_PASSCODE` を更新 → 再デプロイ |
| **全員を強制ログアウト**（退職・異動・漏洩時） | `ACCESS_SECRET` を更新 → 再デプロイ。発行済み Cookie がすべて無効化される |
| 自分だけログアウト | ポータル右上の「ログアウト」 |

共有パスコード方式のため**誰が閲覧したかは記録されません**。
個人単位の追跡や即時失効が必要になった場合は、Vercel Pro の Password Protection、
または独自ドメイン＋Cloudflare Access（メール OTP）への移行を検討してください。

---

## 5. 運用上の注意

- パスコードは Slack の**非公開チャンネル**でのみ共有する（公開チャンネル・メール転送は不可）
- リポジトリ・スクリーンショット・議事録にパスコードを書かない
- 定期的（半期ごとを推奨）に `ACCESS_PASSCODE` / `ACCESS_SECRET` をローテーションする
- ブルートフォース対策は「失敗時 600ms の遅延」＋「十分に長いパスコード」で担保している。
  短い・推測しやすい文字列を設定しないこと
- `vercel.json` で全レスポンスに `X-Robots-Tag: noindex` を付与し、検索エンジンにも載らないようにしている
