01 Premise

前提 — 新規ユーザーの意向ステージ

S1 確信層
このACに決めている／今すぐ買う。オンサイトCVRは健全で、伸びしろは小さい。
S2 比較検討層最優先
買う気はあるが「これ」を決めかね、複数ACを見比べている。新規の「AC到達→検討」9.0%（リピーター22.8%）の主因。
S3 絞り込み層
方向（エリア／やりたいこと）は決まったが、具体ACが未定。流入→AC到達（新規 46.8%）で漏れる。
S4 探索層
漠然とした興味で来訪、今は買わない。離脱後に戻す仕組みが必要。
※ 各ステージの根拠・KPI設計の全体像は KPIダッシュボード「何を改善するのか」 を参照。数値は GA4 Property 347074845（日本・28日・bot除外）。
02 Current state

現状 — 探す・比べる導線は既に揃っている。足りないのは「質」と「再訪」

AC・カテゴリ・エリアの実画面には、ランキング／人気カテゴリ／目的別の絞り込み／あなたにおすすめ／合わせてチェック／その他おすすめが既に実装されている。AC ページの直前ページ（リファラー）で流入量を実測すると：
AC到達（②）の流入元シェア（28日）担っているもの
別のACページから約15%（20.6万人）「合わせてチェック／その他おすすめ」＝比較導線
カテゴリページから約20%（24.9万人）ランキング／おすすめ＝発見導線
お気に入り（保存）から約0.9%（6,828人）再訪導線
（参考）検索エンジンから直接外部流入の大半新規検索でACに直着地
読み取り：比較・発見の導線は合計 35%超のAC到達を実際に生んでいる＝機能は出尽くしている。だから「比較枠／絞り込みを"新しく足す"」は効かない。一方で お気に入りからの再訪は0.9%。保存した人すら戻ってきておらず、ここが最大の空き。
＝ 打ち手は「機能を足す」ではなく、① 出している中身の"関連度"を上げる、② 再訪を太くするの2方向。
03 Actions

施策 — 測って関連度を上げる（S2/S3）＋ 再訪を太くする（S4）

A比較・発見導線の「関連度」を測って上げる（S2・S3）最優先
  • 課題比較・カテゴリ導線はAC到達を35%超運ぶが、新規の「検討（②→③）」は9.0%と低い＝量は出ているが質に伸びしろ
  • 原因仮説出している候補（ランキング/おすすめ/関連AC）の関連度・並び順が新規の意向に合っていない。かつ各モジュールのクリック計測が無く、効果を測れず最適化できない
  • 打ち手① 流入元別のコンバージョン計測（BigQuery）で「量はあるが買われない経路」を特定 → ② その経路の関連度・並び順をA/Bで改善（同行程で比べやすい候補・在庫ありを優先）
  • 詳細「カテゴリ→AC」「AC→AC（比較枠）」経由のAC到達が、検索直着地より検討・購入に進むかを比較。弱い経路の中身を、同エリア×同カテゴリ×人気×在庫ありで再構成
計測クエリの考え方（BigQuery）
① 流入元別のAC到達→検討→購入
  1. GA4 BigQuery export を使い、AC ページの page_referrer を「カテゴリ／別AC／検索／お気に入り」に分類
  2. その経路ごとに ②→③（カレンダー閲覧到達）率・購入率を算出 → 量はあるが弱い経路を特定
② 関連度の指標
  1. 同エリア・同カテゴリ一致率／在庫あり率／クリック後の②→③率 を経路別に見て、関連度が低い面を改善対象にする
※ モジュール別のクリックイベントは未計装。まずは page_referrer ベースで経路の質を測り、必要ならクリック計測を追加。
②→③ の質まず計測 → A/B迷わず買う
B「今は買わない」新規を、最適なタイミングで連れ戻す（S4）最大の空き
  • 課題お気に入り保存からの再訪は0.9%（6,828人）。保存した人(15,362人)すら戻らず、意向を取りこぼしている
  • 原因仮説保存のハードルが高く、保存後に戻る理由（価格・残枠の変化通知など）が無い
  • 打ち手① ワンタップ保存＋保存リストからの予約導線、② 保存ACの値下げ・残枠を通知、③ 閲覧内容に沿った後追い配信
  • 詳細下記。①はサイト内、②③は Braze（CRM）。「保存→予約」の相関計測を整備した上で進める

B-② 価格／残枠リマインドの Braze 設定（ロジック・必要データ・手順）
① データソース
  1. GA4 BigQuery export events_*（保存イベント GA4_vtjp_ex_yokka_add_wishlist）
  2. AC マスター（価格・在庫。商品DB or 在庫API）
② 生成クエリ（BigQuery・1日1回）
-- 直近60日の「保存者 × 保存AC」
SELECT user_pseudo_id AS uid,
       (SELECT value.string_value FROM UNNEST(event_params)
        WHERE key='ac_id') AS ac_id,
       MAX(event_timestamp) AS saved_at
FROM `proj.analytics_347074845.events_*`
WHERE event_name='GA4_vtjp_ex_yokka_add_wishlist'
  AND _TABLE_SUFFIX >=
      FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE(),INTERVAL 60 DAY))
GROUP BY uid, ac_id;
-- ↑ を AC マスターと JOIN し
--   「前日比 価格↓」or「残枠 ≤ 5」の行だけ残す
③ 実行環境・スケジュール
  1. Cloud Scheduler（毎朝1回）→ Cloud Functions でクエリ実行＋整形
④ Braze への投入経路
  1. Braze REST /users/track でカスタム属性を上書き（or CSV import）
⑤ カスタム属性スキーマ（上位3件まで）
  1. wishlist_1_name (string) / wishlist_1_price (number) / wishlist_1_stock (number)
  2. wishlist_1_pricedrop (boolean) / wishlist_1_url (string)。_2 / _3 も同形
⑥ 属性更新の仕組み
  1. 日次バッチが /users/track で属性更新 → Braze Canvas を 「pricedrop=true」属性変化でトリガー発火
⑦ Liquid テンプレート（Content Card 1枚）
{% if ${wishlist_1_pricedrop} == true %}
保存中の「{{${wishlist_1_name}}}」が値下げ！
今 ¥{{${wishlist_1_price}}}（残り{{${wishlist_1_stock}}}）
👉 {{${wishlist_1_url}}}
{% endif %}
⑧ 稼働責任
  1. 初期セットアップ（BQクエリ・Cloud Functions・Braze属性/Canvas）＝エンジニア＋AI coding
  2. 以降は Scheduler＋Braze のマネージドで自走。文言・出し分けはマーケが管理
B-③ 閲覧ベースの後追いナーチャリングの Braze 設定（Connected Content）
① 必要データ → 属性
  1. GA4 BQ の view_item から直近の閲覧エリア/カテゴリを集計
  2. 属性 last_viewed_area / last_viewed_category を /users/track で日次更新
② レコメンドの出し方（Connected Content）
  1. おすすめAC一覧を返す軽量API（例：/reco?area=◯◯&limit=3）を用意
  2. 配信時に Braze が API を叩いて中身を差し込む（在庫・価格は配信時点で取得＝鮮度OK）
③ Liquid（Connected Content 実例）

   :save reco %}

{% endfor %}
④ 配信トリガー
  1. Braze Canvas：離脱後 X 日で Push/メール。属性 last_viewed_area が有る人に限定
⑤ 稼働責任
  1. 初期＝reco API＋属性設計（エンジニア＋AI coding）。以降はマネージド
